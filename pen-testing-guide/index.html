NEX•US PEN TESTING — ALL-ACCESS GUIDE

Test every access level you are authorized to hold, one at a time, and prove what each level can and cannot do.

← Back to the hub — mynexus.world  ·  Planned live: https://mynexus.world/pen-testing-guide/

RULE ZERO, BEFORE ANYTHING ELSE: test only systems you own, or systems you have written permission to test, in writing, from the owner. No permission, no test. That rule is what separates a pen test from an attack, and it is what keeps you, your crew, and your clients safe.

“All access” in this guide does not mean “break into everything.” It means test every access level you are authorized to hold — Unauthenticated visitor, Technician / standard user, Manager / team lead, Admin / owner — one at a time. If a level can see, change, or export something it should not, that is a finding — even if you are the owner testing your own site.

1. What “immortality” means here

Not invulnerability, and not a promise no one will ever find a flaw. Immortality here is durability:

  1. The test is written down, so it survives one person, one night, one phone.
  2. Every finding has evidence, a fix, and a retest.
  3. The next test starts from the last report, not from zero.
  4. Secrets, once exposed, are treated as compromised and rotated — deleting them from the current file is not enough if they are in history, in a download, or in a screenshot.

Build the system so the knowledge outlives the test. That is the whole point of this guide.

2. Roles, not a permanent roster

Run each test as one consolidated report to the owner. Assign a checker to each hat below for that test. You do not need a permanent team to use the hats — you need a clean handoff and one person consolidating the results.

HatJob on this test
GlassSee, act, verify. Never call it fixed without evidence.
LensThe detail everyone else scrolled past: headers, storage, small print.
MeshScore it. Ten opinions in, one severity out.
ForgeShip the fix clean. No secrets in chat, code, or screenshots.
KernelTell the story: what breaks, for whom, and what it costs if ignored.
BrowlserHands on the machine. Click it, do not just read about it.
OperationsStaging first. Preview before anything touches production.
PIX BridgePatient watcher. Never type a password or code alone.

Lil Ant’s job in this model is the same as in FieldPulse work: consolidate the checkers into one exceptions report, not a dump of everything that was fine.

3. Rules of Engagement (ROE) — fill this in before you start

Copy this block into every test report. No ROE, no test.

  • Target(s), exactly: e.g. your own staging copy of a site, your own repo, your own device in a lab.
  • Out of scope, exactly: employer systems, client systems, other people’s accounts, live production data, other people’s devices. If it is not listed as in scope, it is out of scope.
  • Owner permission: name, date, and where the written permission lives.
  • Time window: start / stop, timezone.
  • Allowed: read-only checks, role tests in staging, configuration review.
  • Not allowed: destructive tests, denial-of-service, password guessing against live accounts, exfiltrating real crew/client data, testing a system you do not own, social engineering real people without their consent.
  • Stop conditions: stop immediately on: a live account lockout, a real data exposure, a system going down, or any sign you are outside scope. Report it, do not push through it.
  • Evidence handling: screenshots and logs go in the test folder only. Redact passwords, codes, tokens, and personal data before they go in a report.

4. The test, phase by phase

Phase 0 — Inventory (passive only)

  • List every asset in scope: domains, repos, Netlify sites, pages, forms, login gates, and data stores (including localStorage-only apps).
  • Note what each asset is for, who should access it, and what data it holds.
  • Check public exposure: is a “private” site actually returning a login gate, or loading publicly? Verify live, do not assume a setting worked.
  • Check repo history for your own projects: old secrets, old gates, old links. Treat anything once public as known, and rotate it rather than just deleting it.

Phase 1 — Unauthenticated access

Test as a visitor with no login, in staging first:

  • Can a visitor load a page, file, or export that should need a login?
  • Do direct URLs bypass a gate that the navigation hides?
  • Are old versions, old files, or old links still reachable?
  • Does an error page leak paths, versions, or internal details?
  • Are security headers present on the live response? Note what is missing, do not just assume the platform handles it.

Phase 2 — Technician / standard user access

Log in as the lowest authorized role you own:

  • Can this role see manager tools, manager links, or admin pages?
  • Can it edit, delete, or export records belonging to someone else?
  • Can it change its own role, or a URL parameter, to gain a higher role?
  • Are saved records tied to stable IDs, or do they shift when content changes?
  • Does an export include fields this role should not see?

Phase 3 — Manager / team lead access

Repeat Phase 2 as a manager, and check the boundary both ways:

  • Can a manager see admin-only settings, other teams’ private data, or owner controls?
  • Can a manager share a private link in a way that makes it public?
  • Is there a real sign-in behind manager tools, or only a code in a public file? A client-side code in a public file is not authentication.
  • When a manager leaves the team, is their access actually removed? Test the removal, do not just check a setting.

Phase 4 — Admin / owner access

  • Is admin access protected by a real team/org login, not a shared password in a file or chat?
  • Are admin actions logged? Can you prove who changed what, and when?
  • Can an admin accidentally (or deliberately) expose a private site by flipping one setting? Note the setting and the check that catches it.
  • Are backups and exports handled like production data, not like throwaway files?

Phase 5 — Web app checks (your own apps, staging first)

  • Input handling: unexpected input in forms, search, and uploads in staging. Does it break, reflect, or get stored unsafely?
  • Storage: what lives in localStorage, in URLs, or in exported files? Is any of it a secret, a code, or personal data that should not be there?
  • Secrets in code: search your own repos for keys, tokens, passwords, and old gates. Rotate what you find.
  • Dependencies and links: outdated libraries, third-party scripts, and links that go somewhere you did not intend.
  • Session handling: does logging out actually end the session in your test? Does a shared device keep the next person logged in?

Phase 6 — Devices, Bluetooth, and hardware (lab only)

Only your own devices, only in a lab, never other people’s devices:

  • What does your device broadcast, and to whom? Check it, do not guess.
  • Does a test app leak a name, identifier, or location it should not?
  • Are test features clearly labeled as practice, so no one mistakes a simulation for a real finding?
  • No identifying, tracking, or following real people. A lab device you own is the test subject.

Phase 7 — People and process (with consent only)

  • Phishing or social tests only with written consent from everyone involved, and with a training purpose, not a gotcha.
  • Test the human process too: who gets told when a finding lands, how fast, and who can stop a rollout?
  • Test onboarding and offboarding: new person gets only what they need, departing person loses access promptly.

5. Tools — use the boring, standard ones first

You do not need exotic tools to run a good test. Start here, in a lab or staging:

  • Browser dev tools — network, storage, headers, direct-URL checks
  • A proxy / scanner for your own staging site (OWASP ZAP, Burp Community)
  • A network scanner for your own lab network (Nmap)
  • A secret scanner for your own repos
  • A checklist and a findings log — the most underrated tool in the list

Do not point scanners at live systems you do not own, and do not run aggressive scans against production. Staging first, always.

6. Severity — score it the same way every time

SeverityMeaning
CriticalUnauthenticated access to private data or admin control, or a live secret exposed. Fix and retest before any handover.
HighAn authorized low role can reach a higher role’s data or controls, or a private site is actually public.
MediumA misconfiguration or weak control that needs another step to matter, but is real and repeatable.
LowA hardening gap: missing header, verbose error, outdated library with no reachable path in your test. Note it, schedule it.
InfoAn observation for the next test, not a finding to chase tonight.

If you cannot reproduce it, it is not a finding yet. It is a note for the next test, with the steps you tried.

8. Fix, retest, close — the loop that makes it durable

  1. Fix in staging, not by editing live by hand.
  2. Retest the exact steps from the findings template.
  3. Check the fix did not break the role below it — a manager fix that locks out technicians is a new finding.
  4. Only then promote to production, and re-verify live.
  5. Log it: finding, fix, retest date, and who checked it.
  6. Next test starts from this log. That is how the work survives past one night.

9. Hard boundaries — do not cross these, even with good intent

  • Do not test FieldPulse, your employer’s systems, or any client system unless you have that owner’s written permission for that system, that window, and those tests.
  • Do not test other people’s Netlify sites, accounts, cameras, or devices.
  • Do not use, share, or publish credentials, codes, or tokens you find in a test. Rotate them, redact them, report them to the owner through a private channel.
  • Do not keep testing after a stop condition. Report and stop.
  • Do not call a site secure, compliant, or certified because one test passed. Say what you tested, when, and what is still untested.

10. Quick start — your first authorized run

  1. Pick one system you own. Copy it to staging.
  2. Fill in the ROE block in Section 3.
  3. Run Phases 1–4, one access level at a time.
  4. Write up only the exceptions, with the template in Section 7.
  5. Fix, retest, log it.
  6. Bring the consolidated report back to Lil Ant, and the next run gets shorter, sharper, and harder to fool.

That loop — scope, test, fix, retest, log — is the whole system. Run it, and the knowledge does not die with the test.
